# Проверки перед выпуском

CI запускается для pull request в `main`, push в `main` и вручную через Actions.
Три обязательные группы работают независимо, каждая со своей средой:

| Группа | Что проверяет |
| --- | --- |
| Unit tests and TypeScript | Логика, приватность сводки для ИИ, разбор генерации, правильность ответа после перемешивания вариантов, даты, импорт класса, guards API, типы приложения и тестов |
| API and PostgreSQL integration | Реальные HTTP-роуты, авторизация, сервисы и SQL; миграции с пустой PostgreSQL/pgvector; учебные сценарии, PDF/поиск/генерация, транзакции |
| Browser workflows (desktop and mobile) | Production-сборка Vite, настоящий backend и база, Chromium с настольным и мобильным viewport, клики, Tab/Enter/Space/Shift+Enter, загрузка файла и подтверждение/отмена удаления |

`Deploy tested commit` зависит от успешного завершения всех трёх групп.
Он выполняется только для `main`, никогда для PR. Сервер получает именно SHA
проверенного коммита. Если за время проверки появился новый коммит в `main`,
старый запуск пропускает деплой: новый коммит пройдёт свою проверку.

Для запрета **слияния** красного PR дополнительно настройте в GitHub
Settings → Rules → Rulesets (или Branch protection) обязательные проверки:
`Unit tests and TypeScript`, `API and PostgreSQL integration`,
`Browser workflows (desktop and mobile)`. Файл workflow сам по себе не меняет
настройки защиты ветки.

## Что покрывают сквозные сценарии

- «Проверь решение»: генерация черновика, подтверждение учителем, публикация,
  выбор и три объяснения, одна попытка, скрытие эталонов до проверки, защита чужих
  ответов, сохранение порядка вариантов и версии задания, фоновая проверка,
  история, исправление оценки учителем с сохранением исходного результата ИИ.
  API-тесты проверяют повторы запросов, снятие с публикации во время отправки,
  некорректный ответ модели, три сбоя, ручной повтор, восстановление истёкшей
  аренды задания и запрет устаревшему обработчику перезаписывать результат.
- Вход учителя, неверный пароль, выход, доступ ученика/гостя к закрытым API.
- Добавление/импорт класса, QR-вход, перевыпуск QR и отзыв старого доступа.
- Создание/публикация теста, неправильные и правильные ответы, запрет повторной
  попытки (включая гонку запросов и повторную публикацию), привязка к ученику из cookie, результаты учителя и личный кабинет.
- Прохождение только по личному QR; ключи ответов и объяснения не уходят в
  ученический API до завершения теста учителем. Старые попытки сохраняются и учитываются
  при запрете повторного прохождения. Возврат в черновик доступен из списка тестов.
- Завершение теста закрывает приём (включая гонку с отправкой) и открывает разбор
  только владельцу попытки в профиле. Новые попытки содержат снимок вопросов,
  ответов и объяснений на момент сдачи; правки учителя не переписывают историю.
  Архивные попытки показывают доступные текущие вопросы с явной пометкой.
  Повторная публикация и правка вопросов завершённого теста запрещены.
- Подготовка к ОГЭ/ЕГЭ: материалы и ссылки доступны; тренировочные тесты убраны из библиотеки, профиля и админки, их создание и прохождение запрещены. История прежних попыток сохранена. Общие тесты и задача недели доступны всем.
- Создание задачи, отправка текста/фото, проверка и комментарий учителя,
  публикация и скрытие разбора по одной задаче, повторное открытие приёма.
  Отдельный тест держит блокировку PostgreSQL и проверяет гонку с отправкой.
- Создание/публикация опроса, выбор и изменение ответа, итоговые голоса и профиль.
- Статья/файл библиотеки, публикация и снятие, открытие, статистика просмотров.
- Настоящий PDF → извлечение текста → чанки → векторная запись/поиск →
  генерация/доработка задания → удаление материала.
- Посещения, повтор heartbeat, фильтры статистики, переход к ученику,
  ручной ИИ-анализ и отсутствие личных данных в запросе модели.
- Чат: классификация, ответ, недоступность провайдера; Shift+Enter для переноса
  строки и Enter для отправки.

На границе внешнего LLM используется детерминированный `tests.fake_llm.FakeLLM`.
HTTP приложения, SQL, cookie, файлы и логика сервисов остаются настоящими.
Проверяется интеграция с контрактом провайдера, а не качество/доступность живого
YandexGPT. Браузер подставляет только стороннюю HDR-текстуру оформления и
блокирует остальную внешнюю сеть; API приложения не подменяется.

Эти проверки снижают риск регрессий, но не гарантируют отсутствие всех ошибок.
Голосовой ввод через микрофон, печать на физическом принтере, Safari/Firefox,
нагрузка и работа production-инфраструктуры в этот набор не входят.

## Проверка объяснений нейросетью

Миграция `0012` добавляет отдельные задания и очередь `solution_attempts`.
`YC_MODEL_SOLUTION` (по умолчанию `yandexgpt-5.1`) используется только новым
разделом. Модель должна поддерживать `json_schema` в API completion.
`SOLUTION_WORKER_ENABLED=true` запускает обработчик вместе с API: одна проверка
одновременно на процесс. Несколько процессов разделяют очередь через
`FOR UPDATE SKIP LOCKED`. При остановке процесса задание снова доступно после
истечения трёхминутной аренды; запрос модели ограничен 55 секундами. После трёх
неудач попытка остаётся сохранённой в статусе `failed`, без оценки; учитель может
повторить проверку или оценить вручную. Завершённый результат сохраняется,
просмотр истории не вызывает модель повторно. До сдачи эталоны доступны только
учителю. Выбор оценивается сервером (0/1), три объяснения — по 0/1/2, максимум 7.
При неверном выборе ошибка в выбранном неверном решении остаётся необъяснённой
и получает 0; в правильном решении не требуется находить ошибку.

В интеграционных тестах обработчик вызывается явно, чтобы воспроизвести гонки.
В браузерных тестах работает настоящий цикл очереди с подменой только LLM.
Эти тесты проверяют программный контракт, а не качество математики YandexGPT.
Перед использованием для школьной оценки сравните проверки живой модели с
оценками учителя на правильных, частичных, ошибочных и нестандартных объяснениях.

## Локальный запуск

Нужны Python 3.11, Node 20 и Docker/OrbStack для одноразовой PostgreSQL 16.
Рабочие серверы и рабочая база для тестов не используются.

Из корня проекта:

```bash
backend/.venv/bin/pip install -r backend/requirements-test.txt
npm ci --prefix frontend
cd frontend
npx playwright install chromium
cd ..
docker compose -p mathsite-tests -f docker-compose.test.yml up -d --wait
export TEST_DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:5544/mathsite_test
```

Следующие блоки запускаются отдельно из корня проекта.

Unit-тесты не требуют базы:

```bash
cd backend
.venv/bin/python -m pytest -m 'not integration'
```

Миграции и интеграционные тесты:

```bash
cd backend
.venv/bin/python -m tests.prepare
.venv/bin/python -m pytest -m integration
```

Браузерные проверки (из корня проекта, в том же окружении с `TEST_DATABASE_URL`):

```bash
cd frontend
npm run test:e2e
# Один сценарий или одна конфигурация:
npm run test:e2e -- --project=desktop-chromium --grep weekly
# Пошаговый интерактивный запуск:
npm run test:e2e:ui
```

Playwright сам применяет миграции, запускает тестовый backend на `8001`,
собирает frontend и поднимает preview на `4173`. Занятые порты считаются ошибкой:
существующие серверы не переиспользуются. После прогона тестовые процессы
завершаются. В `TEST_PYTHON` можно указать другой Python с зависимостями тестов.
Локально доступен `PLAYWRIGHT_CHANNEL=chrome` для установленного Chrome;
в CI используется Chromium, установленный для закреплённой версии Playwright.

**База очищается между сценариями.** Скрипты требуют явный `TEST_DATABASE_URL`
и допускают только имя `mathsite_test` или `mathsite_test_<суффикс>`.
Не запускайте интеграционные и браузерные группы одновременно на одной базе.
Для параллельных прогонов создайте отдельные тестовые базы. Compose использует
`tmpfs`, а не volume с данными сайта; остановка удаляет тестовые данные:

```bash
docker compose -p mathsite-tests -f docker-compose.test.yml down
```

Все пользователи, документы и ответы синтетические. Ключи production и файл
`.env` для доступа к YandexGPT не используются. Тестовый провайдер и reset-скрипт
находятся в `backend/tests`; Dockerfile production их не копирует.

## Разбор падения и добавление сценариев

В CI один повтор сохраняет диагностику нестабильного теста; даже если повтор
прошёл, flaky-тест оставляет CI красным.

В GitHub Actions артефакты хранятся 7 дней: JUnit XML, отчёты покрытия backend,
HTML Playwright, screenshots, video и trace упавшего сценария. Локально:

```bash
cd frontend
npm run test:e2e:report
npx playwright show-trace test-results/<сценарий>/trace.zip
```

При новой функции добавляйте тест с наблюдаемым результатом: запрос/действие →
состояние в базе → результат, видимый учителю или ученику. Для исправления бага
добавляйте воспроизводящий его случай. Селекторы UI предпочитают роли, названия
кнопок и подписи полей; ожидания — `expect`/ответ API, а не фиксированные задержки.
Новые PostgreSQL-тесты кладите в `backend/tests/integration/` или помечайте
`@pytest.mark.integration`. Браузерные сценарии — в `frontend/e2e/`.

Нельзя отключать или заменять падающий путь приложения mock-ответом ради
зелёного CI. Для внешних зависимостей расширяйте тестовый провайдер. Отчёты
покрытия доступны как диагностический инструмент; порог процентов пока не
установлен, полнота покрытия оценивается по сценариям.

## Математический батл

Миграция `0013` добавляет раунды, ученические задачи, решения, лайки и историю
оценок. В админке вкладка «Математический батл»: создать черновик раунда,
выбрать проверяющих (учитель / автор задачи / нейросеть), сроки, запустить.
После запуска настройки неизменны. По окончании срока сервер блокирует новые
задачи, решения и голоса; учитель может завершить приём досрочно кнопкой.

Ученик входит по QR и создаёт одну задачу на раунд во вкладке «Моё участие».
Черновик отправляется учителю, который проверяет условие и скрытый эталон перед
публикацией. Повторная публикация не создаёт новое место. Правка текста возможна
только в черновике до срока приёма задач и до первого решения; она сбрасывает
лайки. Снятие с публикации сохраняет решения и оценки, исключает задачу из
ленты и рейтинга авторов до повторной публикации. После поступления решений
условие и эталон менять нельзя, в том числе через API.

Удаление профиля автора не удаляет чужие решения: задача остаётся с подписью
«Удалённый ученик». В текущем рейтинге авторов такой профиль не участвует.
Если требовалась оценка удалённого автора, учитель может заменить её с пояснением.
Уже зафиксированные итоговые таблицы остаются историческим снимком раунда.

На каждую чужую задачу доступна одна окончательная попытка. Идентичная повторная
отправка после сетевого сбоя возвращает прежний ID. Снимок условия сохраняется
с решением. Себе нельзя ставить лайк или отправлять решение собственной задачи.
Автору не показываются имена решателей; чужие оценки скрыты до своей проверки.

Каждый назначенный проверяющий оценивает рассуждения (0–4), вычисления (0–4),
жизненный контекст (0–2). Среднее и рейтинг учитывают только полный набор
назначенных оценок; сбой ИИ не становится нулём. Учитель может заменить отсутствующую
или исправить спорную оценку автора/ИИ с обязательной причиной; история сохраняется,
а ученик не может перезаписать корректировку учителя. Авторский рейтинг — лайки
на опубликованной задаче, рейтинг решателей — сумма средних оценок. Равные баллы
дают одинаковые места; отображение округляется до двух знаков после расчёта.

«Подвести итоги» доступно после завершения приёма и всех проверок. Итоговые
таблицы сохраняются отдельным снимком, изменения оценок/публикаций/лайков
запрещаются. Раунд остаётся в списке с отметкой «Итоги подведены»; открываются
эталонные решения. Нулевая сумма сама по себе не объявляется победой.

Очередь проверки ИИ хранится в PostgreSQL: аренда задания на 3 минуты,
3 попытки с задержкой, восстановление после рестарта. Используется существующий
`YC_MODEL_SOLUTION` и переключатель `SOLUTION_WORKER_ENABLED`; процесс батла
отдельный от очереди «Проверь решение». Устаревший ответ worker не перезаписывает
решение учителя или закрытый раунд. В модель передаются тексты задачи, эталона
и решения, без идентификаторов учеников, имён из профиля и QR-токенов.

Проверки: `test_battles.py` (контракты), `integration/test_battles.py` (настоящие
транзакции, права, ограничения, комбинации проверяющих, очередь, рейтинги),
`frontend/e2e/battles.spec.ts` (полный сценарий учитель → автор → решатель →
три оценки → итоги в настольном и мобильном браузерах). Их подхватывает имеющийся CI.
В тестах заменяется только удалённая модель. Это проверяет поведение приложения,
но не математическую точность реального YandexGPT. Для первого запуска на сервере
нужны миграция `0013`, доступ к YandexGPT и пробное задание с проверкой учителя.
