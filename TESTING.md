# Проверки перед выпуском

CI запускается для pull request в `main`, push в `main` и вручную через Actions.
Три обязательные группы работают независимо, каждая со своей средой:

| Группа | Что проверяет |
| --- | --- |
| Unit tests and TypeScript | Логика, приватность сводки для ИИ, разбор генерации, правильность ответа после перемешивания вариантов, даты, импорт класса, guards API, типы приложения и тестов |
| API and PostgreSQL integration | Реальные HTTP-роуты, авторизация, сервисы и SQL; миграции с пустой PostgreSQL/pgvector; учебные сценарии, PDF/поиск/генерация, транзакции |
| Browser workflows (desktop and mobile) | Production-сборка Vite, настоящий backend и база, Chromium с настольным и мобильным viewport, клики, Tab/Enter/Space/Shift+Enter, загрузка файла и подтверждение/отмена удаления |

`Deploy tested commit` зависит от успешного завершения всех трёх групп.
Он выполняется только для `main`, никогда для PR. Сервер получает именно SHA
проверенного коммита. Если за время проверки появился новый коммит в `main`,
старый запуск пропускает деплой: новый коммит пройдёт свою проверку.

Для запрета **слияния** красного PR дополнительно настройте в GitHub
Settings → Rules → Rulesets (или Branch protection) обязательные проверки:
`Unit tests and TypeScript`, `API and PostgreSQL integration`,
`Browser workflows (desktop and mobile)`. Файл workflow сам по себе не меняет
настройки защиты ветки.

## Что покрывают сквозные сценарии

- Вход учителя, неверный пароль, выход, доступ ученика/гостя к закрытым API.
- Добавление/импорт класса, QR-вход, перевыпуск QR и отзыв старого доступа.
- Создание/публикация теста, неправильные и правильные ответы, повторные
  попытки, привязка к ученику из cookie, результаты учителя и личный кабинет.
- Подготовка к ОГЭ/ЕГЭ: материалы и ссылки доступны; тренировочные тесты убраны из библиотеки, профиля и админки, их создание и прохождение запрещены. История прежних попыток сохранена. Общие тесты и задача недели доступны всем.
- Создание задачи, отправка текста/фото, проверка и комментарий учителя,
  публикация и скрытие разбора по одной задаче, повторное открытие приёма.
  Отдельный тест держит блокировку PostgreSQL и проверяет гонку с отправкой.
- Создание/публикация опроса, выбор и изменение ответа, итоговые голоса и профиль.
- Статья/файл библиотеки, публикация и снятие, открытие, статистика просмотров.
- Настоящий PDF → извлечение текста → чанки → векторная запись/поиск →
  генерация/доработка задания → удаление материала.
- Посещения, повтор heartbeat, фильтры статистики, переход к ученику,
  ручной ИИ-анализ и отсутствие личных данных в запросе модели.
- Чат: классификация, ответ, недоступность провайдера; Shift+Enter для переноса
  строки и Enter для отправки.

На границе внешнего LLM используется детерминированный `tests.fake_llm.FakeLLM`.
HTTP приложения, SQL, cookie, файлы и логика сервисов остаются настоящими.
Проверяется интеграция с контрактом провайдера, а не качество/доступность живого
YandexGPT. Браузер подставляет только стороннюю HDR-текстуру оформления и
блокирует остальную внешнюю сеть; API приложения не подменяется.

Эти проверки снижают риск регрессий, но не гарантируют отсутствие всех ошибок.
Голосовой ввод через микрофон, печать на физическом принтере, Safari/Firefox,
нагрузка и работа production-инфраструктуры в этот набор не входят.

## Локальный запуск

Нужны Python 3.11, Node 20 и Docker/OrbStack для одноразовой PostgreSQL 16.
Рабочие серверы и рабочая база для тестов не используются.

Из корня проекта:

```bash
backend/.venv/bin/pip install -r backend/requirements-test.txt
npm ci --prefix frontend
cd frontend
npx playwright install chromium
cd ..
docker compose -p mathsite-tests -f docker-compose.test.yml up -d --wait
export TEST_DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:5544/mathsite_test
```

Следующие блоки запускаются отдельно из корня проекта.

Unit-тесты не требуют базы:

```bash
cd backend
.venv/bin/python -m pytest -m 'not integration'
```

Миграции и интеграционные тесты:

```bash
cd backend
.venv/bin/python -m tests.prepare
.venv/bin/python -m pytest -m integration
```

Браузерные проверки (из корня проекта, в том же окружении с `TEST_DATABASE_URL`):

```bash
cd frontend
npm run test:e2e
# Один сценарий или одна конфигурация:
npm run test:e2e -- --project=desktop-chromium --grep weekly
# Пошаговый интерактивный запуск:
npm run test:e2e:ui
```

Playwright сам применяет миграции, запускает тестовый backend на `8001`,
собирает frontend и поднимает preview на `4173`. Занятые порты считаются ошибкой:
существующие серверы не переиспользуются. После прогона тестовые процессы
завершаются. В `TEST_PYTHON` можно указать другой Python с зависимостями тестов.
Локально доступен `PLAYWRIGHT_CHANNEL=chrome` для установленного Chrome;
в CI используется Chromium, установленный для закреплённой версии Playwright.

**База очищается между сценариями.** Скрипты требуют явный `TEST_DATABASE_URL`
и допускают только имя `mathsite_test` или `mathsite_test_<суффикс>`.
Не запускайте интеграционные и браузерные группы одновременно на одной базе.
Для параллельных прогонов создайте отдельные тестовые базы. Compose использует
`tmpfs`, а не volume с данными сайта; остановка удаляет тестовые данные:

```bash
docker compose -p mathsite-tests -f docker-compose.test.yml down
```

Все пользователи, документы и ответы синтетические. Ключи production и файл
`.env` для доступа к YandexGPT не используются. Тестовый провайдер и reset-скрипт
находятся в `backend/tests`; Dockerfile production их не копирует.

## Разбор падения и добавление сценариев

В CI один повтор сохраняет диагностику нестабильного теста; даже если повтор
прошёл, flaky-тест оставляет CI красным.

В GitHub Actions артефакты хранятся 7 дней: JUnit XML, отчёты покрытия backend,
HTML Playwright, screenshots, video и trace упавшего сценария. Локально:

```bash
cd frontend
npm run test:e2e:report
npx playwright show-trace test-results/<сценарий>/trace.zip
```

При новой функции добавляйте тест с наблюдаемым результатом: запрос/действие →
состояние в базе → результат, видимый учителю или ученику. Для исправления бага
добавляйте воспроизводящий его случай. Селекторы UI предпочитают роли, названия
кнопок и подписи полей; ожидания — `expect`/ответ API, а не фиксированные задержки.
Новые PostgreSQL-тесты кладите в `backend/tests/integration/` или помечайте
`@pytest.mark.integration`. Браузерные сценарии — в `frontend/e2e/`.

Нельзя отключать или заменять падающий путь приложения mock-ответом ради
зелёного CI. Для внешних зависимостей расширяйте тестовый провайдер. Отчёты
покрытия доступны как диагностический инструмент; порог процентов пока не
установлен, полнота покрытия оценивается по сценариям.
